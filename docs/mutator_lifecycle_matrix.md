# Mutator execution boundaries and evidence

## Scope and baseline

The implementation starts from `834402daade9f62e9dec0b08041dade163a89369`, including the existing proposal constraints, synchronization policies and score-evidence work. The architecture documents refer to an older fixed commit; their proposed backends are not evidence that those backends are registered here. The table below comes from `astrolabe/mutators/base.py`, the case-insensitive `MutatorRegistry`, and the actual runner imports. No registry entry, proposal policy, selector, sample count, native temperature, or acceptance rule was replaced.

The common implementation is `astrolabe/mutators/resident.py` and `astrolabe/mutators/wrappers/resident_daemon.py`. `mutator_terms.<alias>.execution` accepts `legacy`, `daemon`, or `auto`; the factory consumes this execution-only key. `auto` uses the shared broker inside an isolated trajectory. A broker-enabled, GPU-hidden trajectory rejects `legacy` GPU execution. CPU-only mutators retain their original execution path. A standalone `daemon` run is a private serial worker, useful as the resident-serial control.

Measured resource profiles can be supplied through `mutator_terms.<alias>.execution_resources` (or the runner configuration): `resident_bytes`, `scratch_bytes`, `prepared_bytes`, `ram_bytes`, `output_bytes`, `load_ram_bytes`, and `cpu_slots`. These execution-only controls are consumed before native constructors, including ESM constructors that accept no arbitrary runner kwargs. Omitted measurements remain unknown; admission reservations and observed peaks are distinct fields.

## Version and compatibility identities

The baseline superproject pins `vendor/dplm` at `560b299739d537000641b081b962dc573cccb786`, `vendor/esm2` at `43c67d952da30d2471f609848931d20ec8c98532`, `vendor/esm3` at `c79d15480b0111e5a89b69a6aca144c29684dfa5`, `vendor/surfdesign` at `9ce30392b72b65e9cb875e2beb45d607e6f34765`, `vendor/surfpro` at `d728214126b6fdcb5323f76653377614743dd1f3`, and `vendor/na_mpnn` at `835974f3d420de18b3eb1dc66f25fbd17c53cc09`. Effective installed source contents and applied patches are hashed at startup; a gitlink alone is not runtime certification. CarbonDesign and DynamicMPNN take external repositories, so no extra version is invented.

The NA-MPNN AST adapter additionally requires SHA256 `8d8937cceb84fbfc2e1b49b65e21b730a74e9dafab9e9c6720d1af75bda403d7` for `inference/run.py`. Unknown source contents are rejected in resident mode. The native default seed `0` chooses a random seed in each fresh process; substituting a fixed seed would change the protocol. The existing default therefore remains a one-shot backend. Set `NAMPNN.daemon: true` only with an already selected nonzero `NAMPNN.extra_args.seed`; no automatic replay or reseeding is performed.

Every private worker identity includes actual constructor config, code hashes, selected local checkpoint hashes, the external Python environment when present, effective device binding, torch default dtype and relevant deterministic/TF32 flags. All mutator workers currently include a private instance UUID: cross-trajectory initialization sharing is deliberately not certified, because constructors can consume the scientific torch/Python/NumPy RNG. Model construction and every request round-trip the exact owner RNG. GPU-hidden owners store an opaque CUDA state registered at the real scientific seed call; they never initialize CUDA to obtain that state.

Local ESM/DPLM/ESM3 weights must be installed before resident startup. Hub download functions are disabled in the resident worker. This makes environment/model initialization explicit and prevents unbudgeted downloads from entering scientific requests.

## Resource ownership and lifecycle evidence

The trajectory owns accepted state, stage transactions, selection and request identity. The broker owns one ledger per allocated physical GPU. A mutator request has prepare, execute and finalize transport phases with one retained `scientific_request_id` and reservation; only audited CPU methods declare CPU capabilities. Unknown callback, CarbonDesign and DPLM subgraphs execute as `composite`, not falsely as pure forward. Calls retain bounded prepared/RAM/output reservations across phases. Shape keys include tensor dimensions and text/file sizes, rather than backend name alone. Unknown scratch/output memory remains unknown and is admitted conservatively; explicit `execution_resources` hints are reservations, not measured peaks.

Lifecycle reports keep `process_alive`, `weights_loaded`, `gpu_resident`, `ready`, `load_count`, parameter devices/dtypes and child PIDs separate. A private bridge reports unknown model fields when the loader cannot be observed. Nested DPLM/Surf/NA ready messages report successful actual loading sites. Runtime process-tree telemetry remains the release authority: Python `del`, a transport response or a live bridge is not proof of GPU memory release. Private `close(release=True)` fences and reaps the model worker and its descendants. Native wrappers also bound partial-line reads, disable silent restart/replay, and reap failed subprocesses.

The lifecycle reports actual output directories with `scope=job`, and DPLM's existing response pool with `scope=shared_cache`. Shared historical cache bytes are not falsely attributed to the current job and are not deleted as job cleanup. The broker can charge observed growth and audit ownership uncertainty.

## Cache dependencies and scientific semantics

- MPNN CPU parse reuse depends on structure **contents**, selected chains, side-chain parser mode and occupancy handling. Cache entries are copied before modification and bounded by bytes and count. A file changing between prepare and execution is rejected. GPU featurization remains unchanged.
- DPLM pool keys retain the original request dependencies and now include actual local model contents, interpreter/package environment and inference/repository source contents. Pool consumption and refill counts are unchanged. An unresolved remote model identifier is not enough for real cache certification; resident mode requires its local snapshot.
- SurfPro surface keys include native input content, surface vertex count, native seed, tool **content** digests and preprocessing code. SurfDesign adds preprocessing source and the actual PyMOL version to its structure-content key. Surface generation remains CPU work; a cross-environment equivalence claim still requires the real external-version tests.
- No sampled output is memoized as a substitute for another scientific request. Native autoregressive joint decoding, teacher forcing, masks, fixed/shared segments and selector/acceptance logic remain in their existing owners.
- `Mutator.mutate` wraps both ordinary and transition-consistency reference computations in `scientific_operation`; selection/output application remains outside this execution context. Each reference input has its own evidence identity.
- Unknown outcomes do not retry. The runner is fenced and result artifacts are retained until the owning session establishes process termination. Release failures remain visible on repeated `close`; failed startup also retains its bootstrap when no client handle was returned or release could not be confirmed. Private temporary artifact directories are detached from automatic garbage-collection cleanup in these cases. Incorrect phase order, reused prepared state and mismatched response IDs are rejected.

## Reproducible validation

```bash
PYTHONPATH=. python -m pytest -q \
  tests/test_mutator_resident_runtime.py \
  tests/test_mutator_subprocess_protocol.py \
  tests/test_mutator_additional_lifecycle.py \
  tests/test_dplm_lifecycle.py \
  tests/test_dplm_runner_response_cache.py \
  tests/test_surfdesign_mutator.py \
  tests/test_surfpro_mutator.py \
  tests/test_ligandmpnn_device_binding.py \
  tests/test_real_dynamicmpnn_adapter.py
```

`test_mutator_resident_runtime.py` builds the actual ProteinMPNN CPU architecture with a synthetic local checkpoint. It compares two direct requests with two private resident requests, checks complete output/RNG equality, actual load count `1`, CPU binding, cache invalidation and process exit after failure. The NA fixture uses a real torch module to test constructor-RNG preservation under the version-gated AST split. These are mechanism tests; neither fixture certifies trained protein/nucleic-acid model quality or GPU numerical tolerances.

The first isolated remote snapshot completed with 112 passing tests, one skip and one failure in a Path-to-ProDy normalization test; the native parser now receives `str(path)`. The real CPU model's two-request equality and RNG checks passed in that snapshot. Subsequent test snapshots and exact raw logs are recorded by the root integration report. Local stdlib/subprocess/cache/environment tests passed; local full model tests are skipped when torch is absent.

The third isolated remote integration snapshot completed with 377 passing tests, two failures and one skip. All collected mutator tests passed; the two failures concerned a runtime-overlap fixture and an AF2 CPU fixture and were assigned to their respective owners. The fourth snapshot completed with 403 passing tests, one failure and one skip in 469.72 seconds: all backend/runtime tests, including the mutator release-retention fixes, passed. Its sole failure was a benchmark test fixture reading a newly created PID file before its contents were written; that fixture now publishes the PID by atomic rename. The fifth snapshot closed this failure: all 21 focused benchmark tests passed in 2.92 seconds, with one warning and no skips, including the eight process-observer cases and thirteen comparison/timing cases. The real-process cases cover normal exit, lingering children in the same/new session, and externally requested cleanup. These remain CPU integration/mechanism results, including the actual CPU MPNN architecture and synthetic checkpoints, not pretrained GPU-backend or speed certification.

The complete integration interpretation and performance status are maintained in [the runtime implementation report](runtime_implementation_report.md). The focused closure evidence is preserved in [snapshot05-validation.log](../evidence/runtime-20261103/snapshot05-validation.log), with the exact [snapshot05 command](../evidence/runtime-20261103/snapshot05-command.json). No full-suite rerun is implied by the targeted fixture correction.

The final snapshot06 reran 148 affected process-observation, release, CLI, lifecycle, actual CPU ProteinMPNN/synthetic-checkpoint and benchmark tests: all passed with no skips. The final CPU Dummy/MCMC comparison completed all 27 fixed trajectories, with score/decision equivalence and confirmed release in all nine trials. Resident modes were slower for that CPU fixture. These later results and the preserved failed first comparison are documented in the implementation report; they do not upgrade any trained mutator/GPU variant's certification status.

An additional local run of subprocess, DPLM pool/environment and Dynamic lifecycle tests completed with 42 passing tests. It covers no-replay after a DPLM unknown outcome, local-weight cache invalidation, explicit Dynamic factory reuse/close, rejection of stale CLI probability files, and allocation-mask override rejection. A separate integration review reproduced and reported two core defects: GPU composite calls bypassing CPU-slot charging, and nested `OutcomeUnknown` losing its type through JSONL. The runtime owner fixed both and added corresponding core regressions; these fixes are part of the integration evidence rather than a GPU certification claim.

The final focused rerun of these four test files completed with 45 passing tests after adding release-retention regressions. The added cases verify repeated unknown release, startup failure before a client handle returns, bootstrap decode failure followed by unknown release, and artifact survival after garbage collection. These tests exercise failure-state ownership without a GPU or model checkpoint.

Performance conclusions require the common workflow benchmark with fixed hardware allocation, inputs, scientific seed, sample counts, precision and protocol. Interleave legacy direct, private resident serial, and broker adaptive runs; measure cold and steady phases independently. No GPU-throughput improvement, scientific tolerance, pretrained backend certification, or per-backend failure-cleanup certification is asserted solely from these CPU and fake-daemon tests.
